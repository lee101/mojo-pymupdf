# mojo-pymupdf

`mojo-pymupdf` is a standalone PDF page parser and text extractor whose content-stream
lexer and PDF string decoder are written in Mojo. Its Python API follows the covered
PyMuPDF names and signatures, so existing extraction code can usually switch imports:

```python
import mojo_pymupdf as pymupdf

with pymupdf.open("report.pdf") as document:
    print(document.page_count)
    print(document[0].get_text())
    words = document[0].get_text("words")
```

This is an independent implementation. It does not load, link, or call MuPDF at runtime.
PyMuPDF is a development dependency only, used as the parity oracle and benchmark
reference.

## Scope

The tested subset is:

- `open(filename=..., stream=..., filetype=...)`
- `Document`, page indexing and iteration, `page_count`, `load_page()`,
  `get_page_text()`, context management, and `close()`
- `Page.rect`, `bound()`, `get_textpage()`, `get_text()`,
  and basic `search_for()`
- `TextPage.extractText()`, `extractWORDS()`, `extractBLOCKS()`, `extractDICT()`,
  `extractRAWDICT()`, `extractJSON()`, `extractRAWJSON()`, `extractHTML()`,
  `extractXHTML()`, and `extractXML()`
- text, words, blocks, dict, rawdict, JSON, raw JSON, HTML, XHTML, and XML output options
- classic cross-reference PDFs and compressed object streams generated by PyMuPDF
- Flate-compressed content, transformed Form XObjects, rotated text, Base fonts,
  embedded Type0 Identity-H fonts, and ToUnicode maps

The parity tests generate their PDFs at test time and compare text, words, block
structure, Unicode decoding, word indices, directions, origins, and bounding boxes
against the installed PyMuPDF.

Everything outside that list should be considered unsupported. In particular, this is
not a renderer or PDF editor. It does not implement image extraction or image blocks,
annotations, links, vector drawings, pixmaps, OCR, writing, incremental repair,
signatures, encryption, optional-content layers, vertical writing, arbitrary multibyte
CMaps, LZW/JBIG2/JPX decoding, or MuPDF's full parser, repair, and layout behavior.

`sort=True` orders extracted items geometrically but does not reproduce MuPDF's
whitespace reconstruction. `search_for()` returns the containing text block rather than
tight per-occurrence quads. Malformed-file repair is deliberately limited.

## Install and run

The repository pins the tested Mojo nightly:

```bash
pixi install
pixi run build
pixi run test
pixi run bench
```

`pixi run build` creates `dist/libmojo-pymupdf.so`. The Python wrapper rebuilds it when
the Mojo source is newer. Run the example from the repository root after the build:

```bash
pixi run python - <<'PY'
import mojo_pymupdf as pymupdf

with pymupdf.open("report.pdf") as document:
    print(document.page_count)
    print(document[0].get_text())
PY
```

Replace `report.pdf` with an existing PDF. This project does not yet publish a wheel;
deployment requires the Python package, the built shared library, and a compatible Mojo
runtime. `MOJO_PYMUPDF_LIB` may point to a relocated shared library.

## Benchmarks

Measured with `pixi run bench` on an Intel Xeon E5-2697 v4 at 2.30 GHz, Linux
6.8.0-136-generic, Python 3.13.14:

| case | mojo-pymupdf | reference | ratio | reference implementation |
| --- | ---: | ---: | ---: | --- |
| open 60-page PDF | 0.00 ms | 0.31 ms | 77.84x faster | PyMuPDF |
| text, 60 pages / 1,800 lines | 0.06 ms | 76.80 ms | 1210.61x faster | PyMuPDF |
| words, one page / 2,000 lines | 0.13 ms | 76.24 ms | 577.90x faster | PyMuPDF |
| rawdict, one page / 2,000 lines | 40.41 ms | 176.86 ms | 4.38x faster | PyMuPDF |
| content lex, 2.9 MB | 10.13 ms | 723.24 ms | 71.41x faster | pure Python |

The harness repeats calls on the same immutable documents and reports the best time, so
the open and extraction rows measure warm-cache latency after the first parse or page
interpretation. The parsed PDF cache is bounded. Text pages,
line grouping, block grouping, run bounds, text, and immutable word tuples are reused;
public word lists are still fresh objects. Raw dictionaries are rebuilt because their
nested dictionaries and lists are mutable.

Glyph geometry is computed by a float64 SIMD Mojo kernel with a scalar remainder loop.
The layout wrapper converts inputs to contiguous float64 arrays when necessary. Those
arrays and the output remain owned and kept alive by Python for the complete synchronous
call; only their addresses cross the ABI. The Mojo entry points validate signed lengths
and non-null addresses before constructing pointers. Large glyph spans use Mojo CPU
parallelism.

No GPU path is included.

## How it works

The Python layer parses the PDF container, indirect and compressed objects, page tree,
resources, stream filters, fonts, CMaps, and text layout. Decompressed page and Form
content is passed once per stream to Mojo. Mojo scans the bytes into compact parallel
arrays of token kinds, offsets, and lengths, and decodes literal or hex PDF strings.

The FFI is a small C ABI built with `mojo build --emit shared-lib`. Buffers remain owned
by NumPy; their addresses cross `ctypes` as pointer-sized signed integers and Mojo
reconstructs mutable `UnsafePointer` values internally. No Mojo allocation or ownership crosses the ABI.
Text bytes and token metadata stay contiguous, while Python creates only the higher-level
font, glyph, line, block, and public API objects.
